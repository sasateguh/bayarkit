## 4. Callbacks / webhooks — TWO schemes coexist

|                      | **v1 "API-key salt"** (legacy, per-request `webhook` param, plugins)                                                                                                                                                          | **v2 "event webhook"** (dashboard-registered)                                                             |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Registration         | `webhook` field on create (OP marks it deprecated)                                                                                                                                                                            | Dashboard → Developers → Webhook Endpoints, or `POST /v1/webhook-events`. HTTPS + public destination only |
| Delivery             | HTTP POST, **`application/x-www-form-urlencoded`**                                                                                                                                                                            | HTTP POST, **JSON** body; `User-Agent: HitPay v2.0`                                                       |
| Signature location   | `hmac` **field in the form body**                                                                                                                                                                                             | `Hitpay-Signature` **header**                                                                             |
| Key                  | the **API-key salt** (Developers page, beside the API key)                                                                                                                                                                    | **per-webhook-endpoint salt** (shown on the webhook's detail view)                                        |
| Signed string        | every POSTed field **except `hmac`**, sorted by key, concatenated as `key1value1key2value2…` (no separators)                                                                                                                  | the **raw request body bytes**                                                                            |
| Algorithm / encoding | HMAC-SHA256, lowercase hex                                                                                                                                                                                                    | HMAC-SHA256, lowercase hex                                                                                |
| Sources              | EV:1494-1507, EV:1517-1524; SDK:79-88 (`"{$key}{$val}"`, `ksort`, `implode("")`, `hash_hmac('sha256',…)`); WOO:1427-1452 (`$data=$_POST; unset($data['hmac'])`); LF:17666-17671 (TS: `filter(k!=='hmac').sort()`, `${k}${v}`) | EV:58-67, EV:1509-1515, EV:1528-1534, EV:1536-1580; OP:199-208; EV:42                                     |

**v1 fields** (from the official failed example): `payment_id`, `payment_request_id`, `reference_number`, `phone`, `amount`, `currency`, `status`, `error_message` (on failure), `hmac`. Empty fields are sent as empty strings and **must be included** in the signed string. Sources: LF:4138-4143; LF:7005-7009 ("Make sure NOT to include the hmac value…", "Use an empty string if the value does not exist"). The complete list of v1 fields is UNCONFIRMED (no published table). WOO signs whatever arrives in `$_POST`.

**v1 status values** seen: `completed`, `failed`, `pending` (WOO:1462-1520). The plugin also checks `amount == order total` and `currency` before marking paid (WOO:1462-1466).

**v2 headers**: `Hitpay-Event-Type` (`created`/`updated` per EV:63, but `completed` per OP:206, and `failed` per LF:4162) and `Hitpay-Event-Object` (`charge`/`payout`/`invoice`/`order`/`transfer` per EV:64, but `payment_request` per OP:207). The event for a paid payment request is `payment_request.completed` (EV:32, OP:194).

## 6. Contradictions between official materials (most valuable)

1. **Two salts, two schemes.** v1 uses the API-key salt over sorted `key+value` form fields (`hmac` field). v2 uses the per-webhook salt over the raw body (header). OP:205/252 just says "your salt value (from the dashboard)" without saying which one. EV:1492-1531 says they differ. — OP vs EV.
2. **`webhook` param:** OP:311-313 says it is deprecated. OA (CR:144-148) does not mark it deprecated. The **official WooCommerce plugin still uses it** (`setWebhook`, WOO:1670-1683) and verifies v1 `hmac` (WOO:1385, 1452). The SK skill (webhook-events.md:261-272) recommends it "per request".
3. **Express sample re-serialises JSON.** OP:292-293 computes the signature over `JSON.stringify(req.body)`. EV (express.raw) and SK say to use the **raw body**. Re-serialisation can change bytes (whitespace, `\/` and `\uXXXX` escapes, number formatting), so the OP sample can fail verification on a genuine webhook.
4. **Required fields / encoding of create:** OP:69 says `amount`+`currency` are mandatory and form-urlencoded. OA says only `currency` is required, with `application/json`.
5. **Event header values:** EV:63-64 lists `Hitpay-Event-Type` ∈ {created, updated} and an Event-Object list without `payment_request`. OP:206-207 says `completed` / `payment_request`. LF:4162 says `failed`.
6. **Event names:** EV:1511 speaks of `charge.completed`, which is not in the event list (EV:19-36). `charge.failed` is used in EV:52 and SB:106 but is also missing from the list.
7. **Example payloads:** the EV:1416-1427 `payment_request.completed` example is a bank/payout-shaped object with `status:"succeeded"`. OP:214-244 shows a payment-request object with `status:"completed"`. The recurring guide (LF ~6881-6920) labels a **charge** object as Event-Object `payment_request`.
8. **Refund endpoint:** OA, SDK and CLI use `POST /v1/refund` with a required `payment_id` + `amount`. SK refunds.md:11-19 documents `POST /v1/payment-requests/{id}/refund` with an optional amount, which **is not in the OpenAPI**. WOO:1571 says "Only one refund allowed per transaction"; SK refunds.md:372 says multiple partial refunds are allowed.
9. **CLI`trigger`:** docs (LF:1217, /apis/guide/cli) say it "posts a signed payload". CLI trigger.ts sends **no`Hitpay-Signature`**, sets `Hitpay-Event-Type: <full event name>` and `Hitpay-Event-Object: event` — so it cannot exercise signature verification.
10. **`send_sms` default:** the description says "Default is false". The schema says `default: 'true'` (CR:187-196).

## Independent review notes (23 Oct 2026)

The legacy form `hmac` joins key+value without separators, so fields can be re-keyed while the hmac checks; harmless because the UUID `payment_request_id` cannot change. `payments[].status` (`refunded`, `partially_refunded`) is not read: a refunded request still confirms if a callback is replayed before the order was marked paid.
