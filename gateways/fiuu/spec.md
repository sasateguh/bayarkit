# Fiuu (formerly Razer Merchant Services / MOLPay): API contract (hosted payment page + the "3 endpoints")

Researched 2026-10-23. Read-only. Official material only (Fiuu's own GitHub org `FiuuPayment`, plus the legacy `RazerMS` org).

## Is the documentation public?

- **Yes, partly.** There is no HTML developer portal: `docs.fiuu.com` does not resolve, and `fiuu.com/llms.txt` returns the site's HTML "pagenotfound" page. The official API spec is published as a **PDF** in the GitHub repo `FiuuPayment/Documentation-Fiuu_API_Spec`. The latest version is v13.97, dated 25 Sep 2026, 172 pages.
- **Direct Server API: NOT public.** The cheatsheet says it is "NOT published anywhere publicly"; you request it from support@fiuu.com [CHEAT L17]. The Escrow/Mass Payout API is "available upon request only" [DOCREADME].
- There is no OpenAPI or Swagger file. The only machine-readable artefact is a Postman collection (zip) in the same repo.

## 2. Authentication and keys

| Item                        | Value                                                                                                                              | Source               |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Model                       | No API token or OAuth. Integrity is protected by shared-secret **MD5** hashes.                                                     | SPEC p18             |
| Merchant ID                 | Goes in the URL path or `merchant_id` on payment requests; `domain` on most APIs                                                   | SPEC p25, p40        |
| Verify Key ("Confidential") | Signs merchant→PG requests (`vcode`, most request `skey`s). "at least 32 characters".                                              | SPEC p18             |
| Secret Key ("Top Secret")   | Signs PG→merchant responses (payment `skey`, API `VrfKey`). Some requests also use it (reversal, refund).                          | SPEC p18, p106, p107 |
| Mobile XDK                  | Must use different strings for the verify key and the secret key                                                                   | SPEC p19             |
| Domain registration         | Return, callback, notify and cancel URLs on a domain other than the business website must be registered and approved in the portal | SPEC p23; CHEAT L79  |
| Body encoding               | Most APIs take `application/x-www-form-urlencoded`, not JSON. If both GET and POST carry the same parameter, POST wins.            | CHEAT L72            |

## 3. Create payment (hosted payment page)

| Item                | Value                                                                                                                                                                                  | Source        |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| Endpoint            | `POST`/`GET https://pay.fiuu.com/RMS/pay/{MerchantID}/{Payment_Method}`. `{Payment_Method}` is optional (a channel filename). For POST, include the trailing `/` after `{MerchantID}`. | SPEC p25      |
| Plugin path variant | WooCommerce posts to `{host}/MOLPay/pay/{merchant_id}`                                                                                                                                 | WOO L268      |
| Encoding            | UTF-8. POST, GET or a mix.                                                                                                                                                             | SPEC p40      |
| Response            | Browser redirect to the hosted page. There is **no server-side "create" response or payment ID**; `tranID` first appears in the result.                                                | SPEC p12, p45 |

## 4. Result delivery: Return URL, Notification URL and Callback URL

| Item                                   | Value                                                                                                                                                   | Source                       |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| Transport                              | **HTTP POST, form-encoded** ("HTTP POST is the only method"). Values "are not URL encoded" (notification and callback).                                 | SPEC p45, p56, p59           |
| Return URL                             | Browser redirect. Unreliable; do not rely on it.                                                                                                        | SPEC p14; CHEAT L30          |
| Notification URL                       | Server-to-server. `nbcb=2`. The cheatsheet calls it the "most robust" option.                                                                           | SPEC p55–p56; CHEAT L32      |
| Callback URL                           | Server-to-server, for deferred or non-realtime updates (cash, status changes). `nbcb=1`.                                                                | SPEC p58–p59                 |
| Discriminator                          | No `nbcb` = return URL; `nbcb=1` = callback; `nbcb=2` = notification                                                                                    | SPEC p56, p59; WOO L357–L361 |
| Fields                                 | `amount`, `orderid`, `tranID`, `domain`, `status`, `appcode`, `error_code`, `error_desc`, `skey`, `currency`, `channel`, `paydate`, `extraP` (+ `nbcb`) | SPEC p45, p56, p59           |
| Duplicates                             | Multiple notifications for one transaction are possible and do not mean the buyer paid twice                                                            | SPEC p53                     |
| Notify after a DuitNow QR scan         | The notification URL can receive a `status=22` "account enquiry" POST with `extraP={"account_enquiry":"true",…}`. This is not a payment.                | SPEC p138                    |
| IPN ACK for Return or Notification URL | Re-POST every received field plus `treq=1` to `https://pay.fiuu.com/RMS/API/chkstat/returnipn.php`. A front-end JS snippet sends `treq=0`.              | SPEC p53–p57, p66            |
| IPN ACK for Callback URL               | Respond with the plain-text body `CBTOKEN:MPSTATOK`, with no HTML                                                                                       | SPEC p58, p60, p66           |
| Retries                                | "retry for a maximum **3** times, of 15 minutes interval" (SPEC p58), contradicted by "maximum of **4** retries" (CHEAT L38)                            | SPEC p58; CHEAT L38          |

### Status values (return, notification, callback)

| `status` | Meaning                                                                             | Source   |
| -------- | ----------------------------------------------------------------------------------- | -------- |
| `00`     | Success: Authorized, Captured or Settled (except FPX-B2B and FPX-M2E)               | SPEC p45 |
| `11`     | Failed                                                                              | SPEC p45 |
| `22`     | Pending, or "Authorized" for FPX-B2B/M2E (not M2U)                                  | SPEC p45 |
| `-1`     | Not a gateway value: the samples set `status=-1` locally when the `skey` mismatches | SPEC p51 |

### Response field formats

| Field      | Format                                                                                                             | Source                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------- |
| `amount`   | "2 decimal points numeric value", in ringgit                                                                       | SPEC p45                |
| `tranID`   | "integer, 10-20 digits"; recommended as unsigned BIGINT(20). The notification and callback tables say "10 digits". | SPEC p45, p56           |
| `paydate`  | `YYYY-MM-DD HH:mm:ss`. Timezone **UNCONFIRMED**: the spec states none.                                             | SPEC p45                |
| `currency` | "2 or 3 chars". The official WooCommerce plugin normalises a callback currency of **`RM`** to `MYR`.               | SPEC p45; WOO L977–L978 |
| `appcode`  | ≤ 16 characters. Can be empty for some channels.                                                                   | SPEC p45                |

## 5. Payment (response) signature: `skey`

| Item                                         | Value                                                                                                                                                                                                                                                                | Source                                                                     |

## Independent review notes (23 Oct 2026)

The inner hash `md5(tranID.orderid.…)` has no separators: with numeric order ids digits can move between tranID and orderid and still verify. Harmless (the requery is keyed on TranID and answers Fiuu's own record). The fake's requery answer carries `Currency` and a `Q204` amount error that §7 does not document: if real Fiuu omits `Currency`, every confirmation becomes a `mismatch` (fails safe). **Measure.**
