## Adyen traps (each from an official source or a sandbox measurement)

- GET /sessions/{id} needs the sessionResult that only arrives on the shopper's return redirect and its status never updates, and Hosted Checkout sends one AUTHORISATION webhook per attempt, so fulfil only from an AUTHORISATION webhook with success "true" matched on merchantReference, never from a first success "false". *(https://docs.adyen.com/standard/integration/hosted-checkout.md L825-831, L1117, L1228; CheckoutService-v72.json L14641)*
- The Standard-webhook HMAC is Base64(HMAC-SHA256(hex-decoded key, pspReference:originalReference:merchantAccountCode:merchantReference:value:currency:eventCode:success)) with empty slots kept and NO escaping of ':' or '\' inside merchantReference. *(https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures.md L194-229; adyen-java-api-library src/test/resources/mocks/hmac-validation-webhook.json)*
- The live host is not the test host with 'test' swapped for 'live': it is a per-company prefix host with an extra /checkout path segment (https://[prefix]-checkout-live.adyenpayments.com/checkout/v72/...). *(https://docs.adyen.com/development-resources/live-endpoints.md L71)*
- Status enums contain undocumented values (payment link 'paid', session 'active'), so treat unknown statuses as non-final instead of switching on a closed list. *(CheckoutService-v72.json L11680-11681 (PaymentLinkResponse.status), L14641-14642 (SessionResultResponse.status))*

## Rules that apply to every Malaysian gateway

1. Amounts are integer sen. Never compare floating-point ringgit.
2. Never mark an order paid from the return URL or the callback body alone: verify the signature, ask the gateway again,
   then match reference, amount and currency exactly (`confirmPayment` does all three).
3. Gateways retry callbacks, and two customers can pay at once: mark an order paid in one transaction that locks the
   order row, with a unique index on the gateway's payment id, and retry on deadlock (README, "After confirmPayment").
4. Use one reference per payment attempt, so a late callback from an old attempt cannot match a new one.
5. Errors and logs never contain keys or secrets.
6. Save the environment and a fingerprint of the key that created each payment, verify its callback with those
   credentials, and keep an old key configured until its last bill expires.
